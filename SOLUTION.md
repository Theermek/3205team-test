# Решение

## Что сделано

| Коммит | Суть |
|---|---|
| `fix: даты daily-totals с учётом перехода на летнее время…` | дата заказа в таймзоне клиента считается для каждого заказа отдельно; точный перевод рублей в копейки |
| `feat: скидки в daily-totals…` | миграция `002_amount_paid.sql`, приём `amountPaid`, `gross / discount / net` в ответе, ограничение периода 366 днями |
| `fix: гонка при параллельных вебхуках…` | версия заказа сравнивается и сохраняется одним запросом `INSERT … ON CONFLICT DO UPDATE … WHERE` |

### Скидки

- `orders.amount_paid_kop BIGINT NULL` — сколько клиент фактически заплатил, в копейках. `NULL` — внешний API не прислал `amountPaid`.
- `net` берётся из `amountPaid` («сколько клиенты фактически заплатили»), `gross` — из `amount`, `discount = gross - net`, `total = gross`.
- Все суммы считаются в целых копейках и переводятся в рубли только в ответе — так `discount` не превращается в `412.49999…`.
- `amountPaid` принимается числом или строкой, как и `amount`. `amountPaid > amount` или мусор — заказ невалиден (400 для вебхука, `invalid` в синке).
- `discountPercent` не храню: он нужен только чтобы вычислить `amountPaid`, а его API уже присылает. Проверил на всей выгрузке (3853 заказа со скидкой): `amountPaid` всегда равен `amount × (1 − discountPercent/100)`, округлённому до копейки.
- **Заказы, загруженные до миграции.** У них `amount_paid_kop = NULL`, а при повторном синке приходит та же версия (тот же `updatedAt`), которую сервис считает `stale` и пропускает — скидки бы никогда не появились. Поэтому та же версия дозаполняется, если в БД `amount_paid_kop IS NULL`, а в пришедшей он есть.

## Причина расхождения по c_7

Причин две.

### 1. Переход на летнее время (детерминированная, главная)

`TotalsService.daily` брал смещение таймзоны **один раз — на момент запроса** (`tzOffsetMinutes(timezone, new Date())`) и применял ко всем заказам. `c_7` — `Europe/Berlin`, где 29.03.2026 время переходит с UTC+1 на UTC+2. Запрос в ноябре берёт UTC+1, и для 29–31.03 все заказы с 22:00 до 23:00 UTC (00:00–01:00 по Берлину) попадают в предыдущий день. 27–28.03 ещё в зимнем времени — там всё сходится, отсюда «по части дней». Заодно ответ зависел от даты запроса: летом ломались бы как раз 27–28.03.

Исправление: `localDateIn(timezone)` в `src/utils/time.ts` — дата каждого заказа через `Intl.DateTimeFormat` в таймзоне клиента.

### 2. Гонка при параллельных вебхуках (недетерминированная)

`OrdersService.apply` делал `get` → сравнение `updatedAt` → безусловный upsert. Внешняя система шлёт повторы **разных версий** одного заказа пачкой, в пределах одной миллисекунды (видно по перехвату, см. ниже). Два запроса читали старое состояние, оба проходили проверку, и последней могла записаться более старая версия. В моём прогоне так у 4 заказов `c_7` осталась скидка 10% вместо итоговых 33% — `net` за 27.03 и 31.03 был неверным, хотя SQL по той же базе «сходился». Так же может победить `paid` вместо `refunded`, и тогда ломается уже `gross`.

Исправление: `OrdersRepository.saveIfNewer` — сравнение версий внутри `ON CONFLICT DO UPDATE … WHERE orders.updated_at < excluded.updated_at`. Postgres выполняет его под блокировкой строки.

### Как нашёл

1. Код: `new Date()` при расчёте смещения бросается в глаза, а конец марта — переход на летнее время в Европе. Таймзону `c_7` взял из мока: `GET /customers/c_7` → `Europe/Berlin`.
2. Прогон исходного кода (синк + вебхуки) и сравнение с SQL, где день считает сам Postgres (`created_at AT TIME ZONE 'Europe/Berlin'`):

   | день | сервис до исправления | SQL |
   |---|---|---|
   | 27.03 | 24736 | 24736 |
   | 28.03 | 58233 | 58233 |
   | 29.03 | 43964 | 34658 |
   | 30.03 | 52201 | 59684 |
   | 31.03 | 44064 | 35401 |

3. Гонку нашёл на проверке готового `result.json`: независимый пересчёт (выгрузка мока + перехваченные вебхуки, последняя версия каждого заказа по `updatedAt`) расходился с ответом сервиса и с SQL по `net`. Сравнил заказы построчно — в БД осталась версия на час старее. В перехвате эти версии пришли в одну миллисекунду.

## Как проверял

- `npm run typecheck`, `npm test` — 42 теста (было 27), все зелёные.
- Каждый новый тест на исправление запускал на исходном коде — падает (DST, копейки, гонка — последняя 3 из 3 запусков).
- DST-тест покрывает обе стороны перехода, поэтому старый код его не проходит ни зимой, ни летом.
- Полная выгрузка мока (`/orders`, 5030 заказов) и анализ данных: какие поля и типы приходят, совпадает ли `amountPaid` с процентом, как устроены даты без зоны.
- Перехват вебхуков своим HTTP-сервером: что, в каком порядке и как плотно отправляется.
- `result.json` получен по шагам из TASK.md (`docker compose down -v && up -d` → `POST /sync` → вебхуки → `daily-totals`) **дважды** — ответы побайтно совпали. Сверен с SQL по базе и с независимым пересчётом из сырых данных без кода сервиса — совпадает до копейки.

## Что ещё заметил

**Внешний API**
- Rate limit иногда приходит как `200 {"error":"rate_limited"}` — в клиенте это уже обработано, ловил при выгрузке.
- 288 заказов с `createdAt` без зоны. Проверил, что это действительно UTC: задержка до `updatedAt` (всегда с `Z`) у них распределена так же, как у остальных; будь это местное время, было бы смещение на час-два.
- `amount` (157 шт.) и `discountPercent` (177 шт.) иногда строки (`"3100.00"`, `"7"`).
- У 1177 заказов нет `discountPercent`/`amountPaid` вовсе.
- Скидка заказа может меняться уже после оплаты (вебхуки с другим `discountPercent` и новым `updatedAt`).
- У `refunded`-версий `amountPaid` остаётся прежним — не обнуляется.
- Вебхуки: повторы, не по порядку и пачками по одному заказу (см. гонку). Подписи или секрета в запросах нет.

**Код**
- `toKop` терял копейку на float: `Math.floor(4184.6 * 100) = 418459`. Из 100 000 сумм от 0.00 до 999.99 так ломались 4586. Исправил, сохранив отбрасывание долей копейки (существующий тест `10.999 → 1099`).
- `/webhooks/order` без аутентификации — кто угодно может подделать заказ и статистику. Нужна подпись (HMAC) или общий секрет, это договорённость с командой API.
- `/sync` тоже открыт и запускает долгий проход по внешнему API. Параллельные вызовы склеиваются в один, но защиты нет.
- `daily-totals` строил элемент на каждый день без ограничения: `from=1900-01-01&to=2100-01-01` — 73 000 элементов. Ограничил 366 днями.
- Таймзона клиента кешируется навсегда — если клиент её сменит, статистика продолжит считаться в старой.
- Невалидные заказы при синке только считаются (`invalid`), но не логируются — не понять, что именно отброшено.
- `.env` не загружается (нет dotenv) — сервис работает потому, что значения по умолчанию в `config.ts` совпадают с `.env.example`.
- 502 отдаёт клиенту кусок тела ответа внешнего API.

## Допущения

- `net` = `amountPaid`, а не пересчёт из `discountPercent`: по описанию это «сколько клиенты фактически заплатили», и на данных они совпадают.
- Нет `amountPaid` → скидки не было, `net = gross`. Поля появились в API недавно, у старых заказов их нет.
- В статистику по-прежнему идут только `paid`; день — по `createdAt` в таймзоне клиента, как было.
- Существующие тесты `daily-totals` сравнивали ответ целиком (`toEqual`), а формат ответа задание расширяет. В трёх тестах дополнил ожидания полями `gross/discount/net`, не меняя проверяемого смысла.
- Ограничение периода 366 днями — моё решение, в задании его нет.
